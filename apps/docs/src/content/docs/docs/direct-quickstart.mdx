Run a command in a sandbox from your own TypeScript application. You'll need a provider account and **Bun** to run this example. The SDK also supports server-side [Node.js](/docs/providers/support/#runtimes).

## 2. Add your credentials

Create an untracked `.env.local` file in your project root (the repository root for Modal):

<Tabs syncKey="quickstart-provider">
  <TabItem label="boxd">

```sh title=".env.local"
BOXD_API_KEY="<your-boxd-api-key>"
BOXD_ORG="<your-org-id-or-slug>"
```

`BOXD_ORG` is the ID (`org-…`) of the org your key belongs to; `boxd auth --json` lists your orgs with their IDs. The example uses boxd's default image with internet access; set `network: "blocked"` or an allowlist to restrict it.

  </TabItem>
  <TabItem label="Freestyle">

```sh title=".env.local"
FREESTYLE_API_KEY="<your-freestyle-api-key>"
```

The example uses Freestyle's default VM image with internet access.

  </TabItem>
  <TabItem label="Daytona">

```sh title=".env.local"
DAYTONA_API_KEY="<your-daytona-api-key>"
```

The example uses the `daytona-small` Linux snapshot in `us`. Select an active snapshot available in your region. `daytona-default` permits Daytona's essential services; it does not mean all egress is blocked.

  </TabItem>
  <TabItem label="E2B">

```sh title=".env.local"
E2B_API_KEY="<your-e2b-api-key>"
```

The example uses E2B's public `base` template. No team ID or custom template is required.

  </TabItem>
  <TabItem label="Boat (experimental)">

```sh title=".env.local"
BOAT_API_KEY="<your-boat-api-key>"
```

Create an API key in the Boat dashboard. The example starts a full Ubuntu VM with internet access.

  </TabItem>
  <TabItem label="Runloop (experimental)">

```sh title=".env.local"
RUNLOOP_API_KEY="<your-runloop-api-key>"
```

Create an API key in the Runloop dashboard; sign-ups are by invitation. The example uses the default Devbox image with internet access.

  </TabItem>
  <TabItem label="Archil (experimental)">

```sh title=".env.local"
ARCHIL_API_KEY="<your-archil-api-key>"
```

Create an API key in the [Archil console](https://console.archil.com). The example runs in `aws-us-east-1` with internet access, which needs a paid Archil plan. On the Free plan, add `network: "archil-managed"` to `config`.

  </TabItem>
  <TabItem label="exe.dev (experimental)">

```sh title=".env.local"
EXE_API_KEY="<your-exe-dev-token>"
```

Create a token with `ssh exe.dev token` (see [API tokens](https://exe.dev/docs/https-api)). exe.dev VMs have internet egress.

  </TabItem>
  <TabItem label="Vercel (experimental)">

```sh title=".env.local"
VERCEL_TOKEN="<your-vercel-token>"
VERCEL_TEAM_ID="<your-team-id>"
VERCEL_PROJECT_ID="<your-project-id>"
```

Use an existing Vercel team and project. The example uses Vercel's default Node image with internet access.

  </TabItem>
  <TabItem label="Modal (experimental)">

```sh title=".env.local"
MODAL_TOKEN_ID=your-modal-token-id
MODAL_TOKEN_SECRET=your-modal-token-secret
MODAL_APP_NAME=your-existing-app
MODAL_IMAGE_ID=im-your-existing-image-id
```

Use an existing Modal App in the `main` environment and an existing prepared image containing `/bin/sh` and standard shell utilities. The example does not create an App or build an image.

  </TabItem>
</Tabs>

Add `.env.local` to your `.gitignore`. Keep credentials on the server and out of browser code. Running the example creates a sandbox in your provider account and may incur usage charges.

You should see `Hello from Beachside!`. Every example except Modal uses `sandboxes.with()` to clean up the sandbox after the callback succeeds or throws. An outer `finally` closes the client. The experimental Modal example shows manual sandbox cleanup. `close()` alone does **not** destroy compute. If creation or cleanup has an uncertain outcome, follow [Errors and recovery](/docs/guides/recovery/) before retrying.

For temporary work, prefer [scoped sandbox cleanup](/docs/guides/resources/#create-and-clean-up). The scope retains snapshots and volumes, and cleanup failures preserve the callback result or error plus recovery information. Use manual `create()` when the sandbox should outlive the callback.

## Bound connection waits

`Beachside.connect(adapter, { signal, timeoutMs: 30_000 })` accepts `ConnectOptions`.
The advanced definition/config/credentials form accepts the same controls in its options object.
`await client.close({ signal: cleanupSignal, timeoutMs: 5_000 })` accepts `CloseOptions`.
Only positive finite safe-integer budgets are accepted; longer budgets are allowed.

**Compatibility change:** setup now defaults to a 30-second local wait and each close call defaults to a 5-second local wait. These budgets do not change sandbox lifetime, command deadlines or remote compute. Setup cancellation reports `WAIT_ABORTED`; expiry reports `TIMEOUT`, with effect `none`, cause and a phase-specific message. Aborting the setup signal after the client returns has no effect on the usable client.

Close immediately prevents new work and starts local cleanup once. Cancelling or timing out one close wait leaves that attempt running; a later close can wait for it. Cleanup runs in reverse registration order. A hanging hook can leave later hooks pending; failed releases are sent to `onDiagnostic` and remaining cleanup continues. Successful close means registered cleanup was attempted, not that every failed release succeeded. Late resources from abandoned setup are released locally. Neither setup failure nor close deletes sandboxes, volumes or snapshots; use explicit resource operations for those actions.
